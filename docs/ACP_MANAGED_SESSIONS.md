# ACP 托管会话

> 状态：CURRENT，当前源码已实现；不表示此前发布的安装包包含本功能。
> 实测环境：2026-09-04，Windows、Node.js 24.18.1。术语见 [TERMINOLOGY.md](TERMINOLOGY.md)，实现决策见 [ADR 007](adr/007-acp-managed-sessions.md)。

托管会话让你在 RambleDesk 创建 Agent 会话、发送任务、处理权限和反馈。RambleDesk 启动外部 ACP 程序，Agent 仍负责推理与工具执行。原来的 MCP、Pi、dsh 反馈适配器继续可用；适配器支持某个宿主，不等于已经验证该宿主的 ACP 入口。

## 开始使用

1. 在运行 RambleDesk 的机器上安装所选 Agent 或 ACP bridge，并完成它所需的认证。当前没有 Agent 自动安装或更新器。
2. 打开「设置 → Agents」，选择预设或填写自定义配置，保存名称、后端标识、启动命令、参数和环境变量。预设只填默认值，不会安装程序。
3. 点击「检查连接」。它启动临时实例完成 ACP 握手、检查后端是否宣告托管反馈必需的 HTTP MCP 能力，再回收实例；缺少该能力会明确报检查失败。成功仍不表示真实模型、反馈工具、权限及恢复均已通过完整验收。
4. 从会话列表新建托管会话，选择已启用的配置，填写工作目录和标题。目录必须是 **Backend Runtime 所在机器上的现有绝对目录**；浏览器文件选择器不能代替这个目录。标题只给会话命名，不作为第一条任务自动发送。
5. 会话创建后会尝试启动 Agent；失败时仍保留可见的会话，修复配置后可重试。连接后输入任务。活动区显示输入、Agent 消息、思考、工具调用和错误；权限请求在会话中逐项回答，并展示后端提供的命令、路径或变更详情。详情以纯文本显示，超过 32 KiB 时明确标记截断。
6. Agent 创建反馈请求后，在该会话打开请求并提交。RambleDesk 等待当前轮次结束，再把反馈续接消息发送到原 Agent 会话。无需回到另一个 Agent 界面完成 continuation。

桌面与 Web 工作台调用同一个后端会话管理服务。切换客户端不会创建另一个 Agent 会话；Web Access 的启停也不拥有 Agent 生命周期。

## 启动配置

命令栏只填写一个可执行程序名称或路径。每个参数单独一行，不把整条 shell 命令粘贴进命令栏；参数不会进行 shell 展开。环境变量每行使用 `KEY=VALUE`，值中的 `=` 会保留。工作目录属于会话，同一配置可以用于不同项目的多个会话。

| 入口 | 命令 | 参数，每项一行 |
| --- | --- | --- |
| 社区 DeepSeek ACP | `deepseek-acp` | 无 |
| 官方 DeepSeek Harness | `dsh` | `--profile`、`acp` |
| 直接使用 Node 入口 | `node` 或 Node 的绝对路径 | 已安装包的 `lib/bin.js` 绝对路径；官方 dsh 再加 `--profile`、`acp` |

Windows 使用 npm 安装的启动器时，也可使用上表的 Node 入口定位具体版本。实测采用隔离安装包的 Node 入口，准确版本和路径结构见 [后端实机记录](ACP_BACKEND_PROBE.md)。

如果检查提示找不到启动命令，先确认程序已安装且能从启动 RambleDesk 的环境访问，或填写可执行文件的绝对路径。新安装后可能需要重新启动 RambleDesk 才能继承新的 PATH。DeepSeek ACP 与 DeepSeek Harness 是不同的程序；安装前者不会自动提供 `dsh` 命令。

环境变量覆盖 Backend Runtime 继承的环境。填写在 Agent 配置中的参数和环境值会保存在本机 SQLite 数据库中；界面隐藏值和诊断脱敏不等于加密凭据库。使用 Agent 自己的凭据文件或启动 RambleDesk 时继承的环境时，无须把同一密钥再填进配置。

保存配置只影响后续启动。正在运行的实例继续使用启动时的配置，工作台会提示配置变化。已有会话引用的配置不能删除或改为另一个后端标识。禁用配置会阻止后续启动，不会自动停止运行中的会话。

| Agent 入口 | 握手与真实模型 | 托管反馈闭环 | 原 Agent ID 恢复 | 验收边界 |
| --- | --- | --- | --- | --- |
| 社区 `deepseek-acp@0.8.0` | 已通过 | 双项目并发，各自创建请求、提交、自动取得反馈并返回各自标记 | 整个 application/server/store 正常关闭重开后显式恢复原 ID；协议探针验证 load，Rust 客户端验证 resume | 删除 A 后 B 保持连接与原 ID |
| 官方 `@deepseek-ai/dsh@0.1.2-rc.1`，`--profile acp` | 已通过 | 同上；官方工具标题只报告 read 完成，不包含完整文件路径 | 同样通过完整关闭重开；使用 resume，不支持 load，不重放历史更新 | 删除 A 后 B 保持连接与原 ID |
| 社区 `deepseek-acp@0.7.0` | 独立协议探针已通过 MCP 调用与模型回复 | 未执行完整托管 application 闭环 | 独立探针 load 与记忆验证通过 | 不从 0.8.0 外推完整兼容性 |
| `pi-acp@0.0.33` | 用户试用完成握手，真实模型未验证 | 不支持：握手未宣告必需的 HTTP MCP 能力，创建托管 Agent 会话前被拒绝 | 未验证 | Pi 原生反馈适配器与此项无关；其他版本须重新检查 |
| Codex ACP 及其他自定义入口 | 未验证 | 未验证 | 未验证 | 自定义配置与预设可用，不声称兼容 |

两条完整实测通过真实 `SessionApplication`、ACP driver、受限 MCP、SQLite 和持久投递 worker，提交步骤由探针调用工作台 application 模拟用户完成。两个项目的反馈标记互不串入。随后整个 application/server/store 正常关闭重开，没有隐式启动 Agent；显式并发恢复后，两个会话保留原 Agent ID，并通过重新绑定的 MCP 再次取得反馈、读取文件和返回原标记。删除 A 后，其本地会话、请求和投递已清理，B 仍连接到原 Agent ID。

两次 harness 均正常退出，没有强制终止；社区与官方运行分别观察到的 9 和 13 个自有后代进程均已退出。这是应用与协议验收，不代替 Desktop/Web 的手工操作验收。真实重启使用正常关闭；异常中断检查点与迟到回调隔离由运行时 fixture 覆盖，未宣称真实 Agent 的异常崩溃恢复或自身历史日志全部写盘。报告和可复现 harness 见 [ACP_BACKEND_PROBE.md](ACP_BACKEND_PROBE.md)。

隔离 Web 预览另完成实际界面操作：配置检查及草稿切换、零请求创建、双会话输入隔离、权限队列与详情、取消、停止/恢复、运行中直接删除，以及独立请求标签提交后自动显示投递完成。提交后的旧快照竞态已修正并复验；未出现手动 continuation 提示。Desktop 同一工作台组件的接线通过编译与 Tauri/HTTP 合同一致性测试，本轮未执行操作系统原生界面的完整手工验收。

后续用户实际使用 Desktop 时暴露了上述验收缺口：后端活动已持久化，但应用变更未转发到 Tauri 事件流，只有切换视图重读才看到完整回复。已补上与桌面 runtime 同寿命的事件转发，并让首次快照等待前端监听注册完成；原生 Tauri emit/listen 与前端连续轮次更新分别纳入回归。另修复托管 MCP 空闲 5 分钟失效的问题，覆盖等待 16 分钟后沿原 transport session 创建、读取和恢复反馈。这些回归使用隔离 fixture，没有重发用户历史任务或调用真实模型。

当前托管反馈入口要求 Agent 支持 HTTP MCP 注入。RambleDesk 使用 stdio ACP，不宣告客户端文件系统或终端执行能力；文件读取和命令执行由 Agent 自身提供。模型/模式等 ACP 动态配置控件、图片输入、任意远程 ACP、共享实例池和自动历史导入不在当前支持范围。

## 反馈投递状态

反馈请求的终态与投递状态是两件事。托管请求提交、批准或取消时，终态与待投递记录一起持久化；原生工具内等待的外部适配器不会因此多收到一次续接。

| 状态 | 含义与操作 |
| --- | --- |
| `pending` | 等待目标会话可接收输入；Agent 忙碌、停止或断开时不会发往其他会话。 |
| `sending` | 已取得该次投递的执行权，正在执行续接轮次，或等待其完成结果成功落盘。 |
| `delivered` | 续接轮次成功完成。**不表示整个任务已经完成，也不是独立的逐字阅读回执。** |
| `uncertain` | 发送或执行过程中断，无法确定 Agent 已处理多少内容。不会自动盲目重放。 |
| `discarded` | 删除会话等流程已撤销这条投递，不再续接。 |

遇到 `uncertain`，先检查会话活动和反馈结果，再由人选择重试投递或确认已处理。重试可能重复执行已经发生的工作；确认已处理则结束这条投递的重试流程。人工确认也会把状态记为 `delivered`，因此不能仅凭该状态推断工具执行或任务完成。

若续接已有结果但暂时无法保存投递状态，运行时只重试保存同一次执行结果，不重新发送 prompt；该会话后续投递继续排队。保存完成前退出应用，下一次启动会把遗留的 sending 转为 uncertain。

托管 MCP 凭据固定绑定一个本地会话。Agent 不能通过改变 `host_session_id` 把反馈拆到另一个工作台会话，也不能读取另一会话的请求。其 transport session 随实例保留，不因等待用户而在空闲 5 分钟后过期；停止或删除会撤销当前凭据并关闭所属 MCP worker，恢复时重新绑定。

## 停止、恢复与删除

一个 RambleDesk 会话对应一个 Agent 会话，并独占一个 ACP 实例。实例可以包含 bridge 及多个子进程；多个任务、执行轮次和反馈请求仍属于同一个会话。

- **关闭视图**：只关闭 Tab 或浏览器视图，Agent 继续运行。
- **取消轮次**：请求停止当前执行，保留会话、历史和反馈。
- **停止 Agent**：关闭该会话拥有的实例，保留本地记录与原 Agent ID；需要时显式启动或恢复。
- **退出拥有 Backend Runtime 的应用**：收尾自有实例；未结束的执行通过持久检查点呈现为中断。重启后查看历史，再显式恢复。
- **删除会话**：直接停止与清理，无需先归档。删除记录先落盘，再撤销访问、停止实例、处理投递并清理本地请求、草稿、附件、反馈包与活动。失败后仍显示删除中，可重试完成；不会重新接受输入。

只要已经绑定 `remote_session_id`，恢复就必须使用该 ID 的 resume 或 load。后端不支持恢复、历史不存在或恢复失败时，会保留原身份与错误，**不会静默 new 一个空会话**。尚未成功建立 Agent 绑定的首次启动失败可以重新尝试创建。恢复本身不会自动重放用户最后一条任务；检查活动后再决定下一条输入。

删除清理的是 RambleDesk 本地数据与它拥有的运行资源，不删除项目目录，也不承诺清除 Agent 自己管理的历史文件或用户独立启动的服务。

## 开发验收入口

`cargo run -p rambledesk-local-server --example managed_loop` 是真实后端闭环探针；需要显式启用及已有模型凭据，配置方式见 [后端验收记录](ACP_BACKEND_PROBE.md)。

界面验收可以使用不调用模型的隔离 fixture：先执行 `pnpm build:web`，再设置 `RAMBLEDESK_MANAGED_PREVIEW=1` 并运行 `cargo run -p rambledesk-local-server --example managed_preview`。它创建临时数据库和两个测试会话，输出本机浏览器地址与临时登录令牌，Website 会话带一条反馈请求。输入普通文本会得到回显；`permission_pair` 展示两个顺序权限，`wait` 保持执行直至取消。这是界面及 application 接线验证，真实 Agent 的 MCP 工具读取由前一个探针验证。

预览进程按 Ctrl+C 退出；非交互运行时也可以在它输出的临时目录创建空文件 `stop-preview` 触发正常清理。预览不会连接用户已有数据库，也不修改全局 Agent 配置。
