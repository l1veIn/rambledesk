# 数据升级与版本回退

## 从 0.4.0 升级到 0.5.0-rc.1

0.5.0-rc.1 将扩展迁移版本从 20 升到 22。迁移 21 加入类型化工作台；迁移 22 扩展请求附件的媒体类型约束，允许音视频材料，并保留原有附件记录及索引。已有请求、草稿和反馈包仍保留。

已发行的 **0.4.0 最多支持扩展版本 20**，会拒绝打开升级后的数据库（`NewerDatabase`）。重新安装 0.4.0 不能直接降级资料库；0.3.3 的历史兼容行为也不代表 0.4.0 支持回退。

升级和回退步骤：

1. 退出所有 RambleDesk 实例；备份数据库所在目录、附件资料库及应用配置。若设置了 `RAMBLEDESK_DATABASE_FILE` 或 `RAMBLEDESK_LIBRARY_DIR`，备份对应位置。保留成套文件，不只复制单个 SQLite 文件或反馈包。
2. 安装候选版并验证原有反馈、草稿和附件；独立保存升级前备份，不覆盖它。自动数据库备份不能替代包含附件和配置的完整备份。
3. 需要回退时，退出候选版并另存当前整套资料，再恢复升级前备份后启动 0.4.0。候选版中新增的反馈不在旧备份里，需先另外保留其反馈包；不能承诺自动合并。
4. 不删除扩展迁移记录、不手工降低数据库版本，也不绕过旧版的版本上限保护。

## 类型化工作台的迁移 21

迁移 21 增加可空的 `feedback_requests.workbench_json`，纳入独立扩展迁移账本。已有请求保持 NULL；旧请求的不可变输入哈希不变。类型请求额外把工作台类型、版本和完整数据纳入哈希。反馈包 manifest 的 `workbench` 是可选字段，旧反馈包仍按原合同读取。

0.3.3 的旧读写 SQL 可以忽略该列，原有反馈及删除仍可执行；兼容回归测试覆盖旧迁移器打开、旧请求写入与再次升级。工作台专属交互不能在旧界面使用，旧客户端保存草稿可能丢弃 `workbenchState` 中的问答答案或文稿批注，提交时也可能生成没有结构化结果的旧格式反馈包。再次升级后不会从 Markdown 推测或补全已丢失的交互数据。历史安装包对类型请求的编辑、提交和完整往返不在兼容承诺内；需要回退时，先备份资料库，并在旧版中仅处理原有无类型请求。

未知工作台的只读保护依赖客户端和服务端已经认识 `workbench` envelope，能够检测不支持的类型、版本或数据。已发行的 0.3.3 不具备这一检测能力，不能因为它仍可打开数据库，就推断它会以只读方式保护新工作台。当前测试验证的是新版识别未来合同后的保护，不是对旧二进制行为的追溯修复。

带扩展版本上限检查、仅支持到 20 的正式版 0.4.0 和相应开发版本会拒绝迁移 21/22 的数据库；这与不读取扩展账本的 0.3.3 行为不同。试验使用临时数据库或独立开发数据目录，不在用户现有资料库上做降级实验。

## 与 0.3.3 的兼容范围

ACP 版本必须既能读取 0.3.3 数据，也允许用户再次运行 0.3.3，然后重新升级。仅仅使用新增表、字段的 SQL 并不能证明这个往返成立：0.3.3 会在查询业务数据之前拒绝 `_sqlx_migrations` 中高于 10 的版本。

当前白名单中的 11–21 号迁移包含独立表及兼容旧 SQL 的字段、索引；迁移 22 重建请求附件表以扩展媒体类型约束，保留原有列、记录和索引。迁移 21 的类型请求和迁移 22 的音视频材料不代表旧界面支持对应功能，另受上面的功能兼容限制。旧版的 1–10 号迁移保持原样；扩展记录到 `_rambledesk_extensions`。已有开发版本写入 SQLx 表的 11–22 号记录，在下一次运行包含此兼容处理的版本时于事务中转换，保留时间戳和业务数据，不重新执行已完成的 SQL。

这不是绕过所有版本检查。未知迁移、校验不符、未完成迁移仍然阻止打开。后续迁移必须单独判断是否影响旧版读写；不可兼容的变化不能直接加入扩展白名单。

## 回退后的行为

- 0.3.3 可以继续处理其原有反馈、草稿、归档及删除操作。
- 0.3.3 无法运行 ACP 会话；仅有 ACP 对话、没有反馈请求的会话不会出现在旧版列表中。配置和会话历史仍保留，重新升级后可用。
- 如果用户在旧版完成了 ACP 反馈，再次升级时将缺失的后续发送记录标为待确认，保留反馈包，由用户决定是否继续，不自动重复发送。
- 用户主动在旧版删除可见反馈或会话时，其相关数据仍按删除语义清理；版本兼容不会撤销用户的明确删除操作。
- 旧版修改主题、侧栏及布局时会保留它不认识的 ACP 标签页快照。旧版不认识新语音模型时可能恢复为旧版默认模型，这不影响会话数据。

如果开发版本曾把 11–22 号迁移写入 `_sqlx_migrations`，需要先成功启动包含上述兼容处理的新版一次，再回退 0.3.3。单独重新安装旧版不会转换迁移记录。不要手工降低版本号或删除迁移记录；应用会核对实际已知迁移并在事务中转换。升级前的自动数据库备份继续保留。

## 启动失败的处理

1. 原生配置、数据库、服务或恢复阶段失败：显示阶段、错误码及适用的数据库版本信息；可以打开日志目录并退出。对话框异步显示，不阻塞负责显示它的主线程。
2. 工作台读取失败或单次读取超过 30 秒：停止对应加载状态，保留错误详情，提供重试和独立的关于/诊断入口。超时不会自动重放写入操作。
3. 界面组件或偏好初始化失败：由不依赖 Svelte、偏好存储及数据库的恢复页面提供重新加载和复制错误信息。加载超时后的组件不会覆盖恢复页面。

如果后端在完成初始化前失败，诊断 ZIP 导出可能不可用；此时使用原生提示中的日志目录。新错误展示不能追溯修改已发行的 0.3.3 二进制。

## 回归依据

- 存储专项测试固定 0.3.3 的迁移校验值，使用旧版迁移器和读写 SQL，覆盖升级 → 回退 → 再升级及失败事务回滚。
- 已使用实际设备数据库的只读副本，以 v0.3.3 标签的原版存储代码独立验证：修复前拒绝版本 20，转换后能读取活动与归档反馈，再次升级也能打开。
- 副本往返后 16 张业务表逐行比较一致，SQLite 完整性检查通过，外键违反数为 0。原设备数据库未被这次验证改动。
- 发布安装包仍需 Windows/macOS 实机验证，尤其是原生错误对话框、退出和重新启动。
