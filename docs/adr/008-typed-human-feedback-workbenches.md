# ADR 008：持久化人类回答与第一方工作台

- 状态：Accepted；具体支持面与验收结果以现行文档及测试证据为准
- 日期：2026-09-26
- 术语源：[TERMINOLOGY.md](../TERMINOLOGY.md)
- 现行合同：[PROTOCOL.md](../PROTOCOL.md)、[ARCHITECTURE.md](../ARCHITECTURE.md)
- 文稿审阅：[document-review.md](../workbench/document-review.md)

## 背景与失效假设

早期 Ramble 以真实产品体验和自由正文为核心：Agent 给出体验动作，人类在 TipTap 中记录意见。这种输入输出适合开放反馈，但逐题问答、方案选择和文稿批注已经带有稳定对象、可修改状态与完整性要求。把一次选择再写成正文，会产生两份含义相同但可能不同步的表示；从正文恢复选项或文本锚点也无法建立确定合同。

三种工作台实验已验证：答案可以独立保存，正文可以只作为补充；两者仍可共用请求身份、revision/CAS、发布与 Agent 续接。用户进一步提出视频脚本和发言稿审阅，需要保留原稿、指向具体段落或文字、表达改写建议，再让 Agent 据提交结果修改。这些真实需求使宪章“回复侧自由”和“短问答不是主要价值”不再足以描述产品范围。

## 决策

### 1. 核心范围包括持久化人类回答与判断

反馈请求可以承载体验、问答、选择与审阅。通用价值是明确材料、可恢复的人类输入、提交前修改、不可变结果以及回到原 Agent 会话。Ramble 保留自由反馈与真实体验优势。权限审批继续走既有权限合同；选择某个方案或给出文稿判断本身不授予工具执行权限。

### 2. 分开输入、草稿、结果和请求处理结果

| 对象 | 所有权与不变量 |
| --- | --- |
| Request input | Agent 提供的不可变材料与 `workbench.type/version/data`；参与幂等比较。 |
| Feedback Draft | 可修改的人类输入聚合；`doc` 与 `workbenchState` 同 revision/CAS 保存，不缓存到布局快照。 |
| Draft Document | TipTap 自由正文；Markdown 只投影正文，Cooking 只整理这一部分。 |
| Interaction State | 类型专属回答、选择、批注或标记；可未完成，正文撤销不改动它。 |
| Workbench Result | 提交时服务端按原始输入校验、解析后的结构化回答，发布后不可变。 |
| Request Outcome | 提交、取消或允许的直接批准；不是选项值、审阅判断或 `completed` 的同义词。 |

既有 `document_json` 字段继续作为版本化 Draft envelope，不因命名迁移数据库。正文和交互状态必须一起冻结提交。服务器重新确定展示标签并验证文本锚点，不相信客户端提交的派生显示内容。结构化完整性不能靠填写正文绕过。

存储层拥有这个 JSON envelope 的编解码，在事务快照中得到类型化状态与正文投影后调用 core 的纯提交策略。core 持有输入、完整性与结果规则，不解析 `document_json` 或依赖 JSON 库。业务事实仍由 Backend Runtime 持有；把 codec 留在存储边界不把领域判断下放给数据库实现。

### 3. 工作台是第一方静态类型，视图独立组合

类型定义输入、状态与结果合同；客户端视图定义呈现。每种视图在独立工作区域内组织自己的交互，不借 Ramble 简报嵌套其他工作台。共享容器保留一套反馈列、采集、草稿队列、提交与交付。新类型不复制这些能力，也不直接依赖 transport、Tauri 或宿主协议。

类型及视图随应用构建，通过静态注册关系组合。Agent 使用用途目录和按需 schema 选择类型，工具数量不随类型增加。目录 `interaction` 是说明元数据；不建立远程插件加载、通用 UI DSL、第三方市场或可互换渲染协议。

`Action` 继续表示 Ramble 的体验动作。问答题、选项和文稿段落各有自身身份；既有 actions 投影仅是兼容桥接，不能成为所有类型的强制领域模型。

### 4. 不理解合同的客户端只读保留数据

新请求的未知类型或版本在服务端拒绝。已经认识工作台 envelope、但不支持某个类型或版本的客户端读取已有请求时，保留输入、正文、状态和结果，只读呈现并说明原因。该客户端不得覆盖保存、提交或直接批准，不能把空状态或自由正文伪装成合法结果。只读不改变请求业务状态，显式取消仍沿用请求级合同。已发行的 0.3.3 不认识 envelope，不能提供这一保护；其降级限制见[数据兼容](../DATA_COMPATIBILITY.md)。

读取 `WorkbenchSpec` / `WorkbenchPackage` 时，先解析类型与版本，再决定使用已知领域类型还是不解释的值。未知输入与已发布结果由格式无关的 `serde-value` 承载；即使其字段看起来像当前 Ramble 或问答，也不能套用当前默认值、删除扩展字段或降成 `null`。JSON 编解码及对应 wire 回归留在存储和传输边界，不为此放宽 core 的依赖约束。

旧的无类型请求保持完整 Ramble 行为与原幂等哈希。早期 `ramble`、`questions`、`single_choice` v1 wire 字段继续兼容；问答 `cancelled:false`、旧单选 `status` 不因新发现目录排除单选而删除。新领域术语不意味着无版本变更地重写已发布包。

### 5. 文稿审阅保留原文，意见独立持久化

`document_review` v1 的原稿由稳定段落 id 和来源版本标识组成。人类可对整段或单段内文字批注、提出替换建议，并显式给出整稿判断。每段复用一条批注，收起后显示文字摘要；删除段落按钮显示可恢复的删除线，修改意见直接写入批注。旧草稿的多条批注和保留／修改标记继续保留，界面不再创建这些段落标记。原稿不能在当前请求中编辑；Agent 读取已提交意见后决定如何修改，再审阅时创建新请求。

文字锚点按 Unicode 标量值半开区间与原文引用共同验证。批注只表达意见和建议，不设待处理／已解决状态；历史状态字段读取时忽略，意见内容继续保留。原文旁可直接展开批注，不提供独立的原文定位操作。首版不承担跨段锚点、多人评论线程、跨版本迁移、视频时间轴或自动应用建议。

## 代价与后果

补充决策（2026-09-26）：独立 `single_choice` 的表达能力由 `questions` 的单题、`allowOther:false` 完整覆盖，因此新发现目录和示例不再提供该类型。旧请求与旧调用方的 wire 输入、幂等身份、草稿和结果仍原样兼容，客户端通过薄兼容层复用问答视图。问答的自定义回答与文稿批注一起接入共享语音会话，不另建采集或提交链路。

类型专属结果不再能仅靠 `feedback.md` 读取；适配器必须指向 manifest 结构化结果，正文只做自由说明。保存和提交需要覆盖正文与答案并发修改的 CAS、恢复与失败路径。未知版本客户端放弃编辑能力，以避免悄悄丢字段；该限制应在界面明确表达。

本轮不增加每类型独立数据库或发布队列。采用已有 envelope 和应用生命周期降低迁移面，但要求所有正文变换保留未知或不参与变换的结构化字段。随着真实类型增加，再依据重复代码和边界证据提取公共组件；注册项数量本身不是架构成功的指标。

## 验收要求

每个类型至少覆盖创建验证、草稿保存与恢复、无正文提交、未完成拒绝、取消和终态读取；共享链路覆盖 revision 冲突、切换请求及正文输入不丢交互状态。文稿审阅另外覆盖中文/emoji 锚点、引用不匹配拒绝、整段批注、建议删除和历史批注去除状态后的内容保留。自动化、浏览器夹具与真实 Desktop/Agent 操作分别记录，不以预览成功宣称端到端验收完成。
