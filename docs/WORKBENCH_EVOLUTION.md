## 1. 已接受的方向

RambleDesk 为人与 Coding Agent 协作提供适合当前任务的反馈界面。体验、问答、选择与审阅都复用持久请求、可恢复草稿、明确提交和不可变反馈包。统一的是反馈生命周期，不是每一种交互都必须变成正文。

每个工作台类型拥有独立业务视图。导航之后的工作区域呈现材料与专用交互，右侧反馈列承载自由正文、语音、截图、附件、保存状态与统一提交。专用视图不能另造编辑器、采集、草稿队列或发布链路；自由正文也不能绕过该类型的完整性要求。

类型随应用构建，采用第一方静态注册。Agent 浏览用途目录，再按需读取所选类型的 schema；新增类型不增加一套等待和恢复工具。当前不做动态插件市场、任意 UI schema 或通用工作流引擎。

## 3. 本轮收口

### 产品与领域

将“持久化人类回答与判断”写入宪章与产品旅程，并区分工作台整体、类型、视图、容器和注册表。Feedback Draft 是正文与交互状态的聚合，Document 只是正文，Result 是校验后发布的回答，Request Outcome 表达提交/取消/允许的批准。

三种既有 v1 wire 形状向后兼容。问答的 `cancelled` 和单选的 `status` 不因术语收口被删除；未带类型的历史请求继续采用 Ramble 与原幂等哈希。Action 保持体验动作原义；历史投影不要求新类型把段落、批注或方案都变成 Action。

### 客户端组合

每种类型使用独立视图与自身业务控件，不通过给 Ramble 简报增加 slot 或模式开关容纳所有交互。共享容器只协调布局、状态和反馈列，注册项连接类型与视图，不拥有额外业务事实。

创建未知合同在服务端拒绝。客户端遇到不认识的已有类型/版本时只读保留原始输入、草稿与结果，显示兼容原因；禁止覆盖保存、提交或直接批准。未知合同不是终态，显式取消仍是请求操作。渲染失败不能降成一个看似成功的空答案。

### 文稿审阅

`document_review` v1 面向视频脚本、发言稿等分段材料。原稿只读，段落有稳定 id 与来源版本；人类通过批注、段落标记和建议改写表达意见，并显式给出整稿判断。文字锚点通过 Unicode 标量值区间与原文引用验证；原稿变化建立新请求。

本轮不直接改稿、不做跨段单条批注、多用户线程、跨版本锚点迁移或视频时间轴。已解决批注仍保留，不等于 Agent 已经修改原文。字段与限制见[文稿审阅设计](workbench/document-review.md)。

## 4. 不变的保存与提交边界

| 边界 | 规则 |
| --- | --- |
| 请求 | 类型、版本、原始专属输入不可变，并参与创建幂等比较。 |
| 草稿 | 版本化 `document_json` envelope 保存 `doc` 与可选 `workbenchState`；正文 Markdown 只由 `doc` 派生。 |
| 一致性 | 正文和交互状态共用 revision/CAS 与保存队列；发布只能使用同一个冻结快照。 |
| 用户输入 | 空正文可以配合有效结构化回答；正文不能伪造选择、跳过必答题或隐式通过审阅。 |
| 整理 | Tidy 维持语音整理语义；Cooking 只处理补充正文，不修改结构化回答。 |
| 结果 | 服务器校验稳定 id、选项和锚点后发布；Markdown 不充当结构化真源。 |
| 取消与批准 | 取消没有作答结果；最终总结批准与普通提交分开，不能绕过类型完整性。 |
| 恢复 | 失败保留草稿；请求切换、后台正文采集和旧回执不能覆盖另一请求或丢弃交互状态。 |

## 5. 验收要求

本轮完成的判断依据是边界成立及真实闭环，不是工作台数量：

- Ramble 原行为与无类型旧请求保持可用。
- 每种类型覆盖创建、保存、恢复、完整性、无正文提交、取消和已发布结果读取。
- 正文与类型状态并发编辑、revision 冲突、切换请求和后台输入保留两部分内容。
- 未知类型/版本数据不被清空，不暴露错误的提交或批准路径。
- 独立类型视图不导入 transport、设备采集或宿主协议，新增类型无需复制容器。
- 文稿审阅验证中文/emoji 锚点、无效引用拒绝、整段批注、建议删除和 resolved 意见保留。
- 静态检查、自动化、浏览器预览和真实 Desktop/Agent 操作分别记录，未跑的项目明确留作待验。

## 6. 后续工作

首次引导与用户启用策略只有在作用域和恢复语义明确后再做。禁用若被引入，应限制新请求选择，不删除已有草稿或使历史结果失去解释方式。

反馈目标可以在需要“语音写入题目或批注”时进一步扩展；仍要固定 request/target owner，复用现有采集管线，不为每个字段创建隐藏 Editor。当前通用语音输入保留在反馈列，不能从 UI 焦点推断稳定归属。

后续类型根据真实需求选择，如排序或更复杂的材料审阅。先完成现有类型的真实反馈闭环，再决定是否需要通用化；无限画布、远程插件、跨行业 SDK、AG-UI/A2UI 接入不作为本轮依赖。
