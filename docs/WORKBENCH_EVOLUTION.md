# 从固定反馈界面到可注册工作台

状态：后续迭代路线；阶段 0、1 已完成，阶段 2 进行中，其余未实现。更新日期：2026-09-16。

本文记录产品讨论中确定的方向、当前代码起点和逐步迁移顺序，供后续按阶段实施。当前运行合同仍以[架构](ARCHITECTURE.md)、[协议](PROTOCOL.md)和[术语表](TERMINOLOGY.md)为准。文中的组件名、注册字段和新协议形状均为建议，不代表现有 API。

## 1. 要解决什么问题

RambleDesk 探索的是：在人与 Coding Agent 协作时，为原本只能写进聊天框的内容提供更适合当前工作的交互界面。人可以回答问题、调整工作顺序、审阅材料，也可以随时自由表达。工作台产生的回答、判断和证据，最终需要可靠地回到原 Agent 上下文。

工作台因此可以有多种形态。问答适合选项和表单；顺序编排适合可拖动、可编辑的卡片；开放反馈适合当前 Ramble 的任务材料与富文本记录。统一的是反馈闭环，而不是所有工作都使用同一种画布或表单。

Agent 无法完整预测人类的表达方式，所以每种工作台都携带通用反馈输入。专用交互帮助用户完成具体动作，TipTap 保留自由表达、补充证据、指出问题设置不合适的路径。

这可作为 vibecoding 场景的 Agent UI 探索方向。当前路线只定义 RambleDesk 自身的工作台合同；AG-UI、A2UI 可以作为后续研究对象，不将接入某个协议或通用 JSON renderer 设为此次重构的前提。

## 2. 已确定的设计方向

| 事项 | 本轮结论 |
| --- | --- |
| 通用输入 | 每个工作台都有基于 TipTap 的自由反馈区，包含文字、语音、截图、附件和整理入口；设备能力与现有配置决定具体可用性。 |
| 输入操作归属 | 语音、截图、剪贴板、附件、整理集中在 TipTap 上方；低频文字格式操作收起，按需展开。 |
| 桌面布局 | 专用工作区在左，通用反馈列在右。右列至少 **700 CSS px**，替代此前误写的 200px。 |
| 提交位置 | 右列包含提交按钮或按钮组，提交整份反馈，包括专用工作区结果、自由表达和附件。 |
| 工作台类型 | 可预置、可注册、可逐步扩展；先有 Ramble 和 AskQuestion 两种。 |
| Agent 使用 | Agent 能从简短说明理解各工作台用途、输入要求和返回内容。 |
| 首次使用 | 每种工作台首次打开时给出简短引导，可关闭，也可再次查看。 |
| 用户选择 | 用户可配置启用哪些工作台；启用配置不能让已有请求和草稿不可访问。 |
| 迭代方式 | 先调整现有 UI，再提取公共结构，再引入注册。每一步保持现有反馈闭环可用。 |

700px 是桌面双列模式下通用反馈列的宽度要求，不是当前右侧按钮栏的简单放大。小窗口、浏览器和手机无法容纳双列时，需要明确的单列或切换视图；具体断点与呈现方式在布局阶段验证。不得用横向溢出勉强维持双列，也不得把窄屏的存在解释为可以继续使用 200px 桌面反馈列。

## 4. 目标结构与责任

以下名称只描述职责，实施时先沿用现有模块，不为名字先建空壳目录。

```text
会话 / 请求导航
└─ 当前反馈请求的公共容器
   ├─ 左：工作台专用区域
   │  ├─ Ramble：背景、体验动作、材料
   │  └─ AskQuestion：问题、选项、局部回答
   └─ 右：通用反馈列（桌面双列模式至少 700px）
      ├─ 输入工具栏：语音 / 截图 / 附件 / 整理
      ├─ TipTap：自由表达与补充说明
      ├─ 附件、保存与处理状态
      └─ 提交按钮组：汇总本次请求的全部反馈
```

公共容器负责加载请求、选择工作台、布局、只读/忙碌状态和统一提交。专用区域负责呈现任务对象、维护其交互状态、提供校验结果和可提交结果。通用反馈列负责自由表达及采集，不要求知道当前工作台的具体问题或卡片结构。

注册表负责“有哪些工作台、适合什么用途、如何创建视图和解释数据”。业务状态仍由现有 application 和 persistence 层管理。注册表不持有 Editor、设备资源、宿主会话或独立发布队列。

### 阶段 3：最小注册架构，先注册 Ramble

**目标：** “显示哪个工作台”从固定组件选择变为明确的注册决策。

首期采用随应用构建的第一方静态注册表。一个注册项只需要足以支持下一种工作台的信息：稳定类型标识、版本、显示名、用途说明、输入校验、视图入口，以及结果提取/序列化能力。哪些字段合并或拆开，由 Ramble 和 AskQuestion 的真实差异决定。

- 默认注册 Ramble；已有请求和未指定工作台的请求继续进入 Ramble。
- 公共容器按类型解析注册项，工作台不跨层修改公共容器或其他工作台状态。
- 区分工作台类型版本、请求数据版本和首次引导版本，避免每次 UI 修改都改变存储协议。
- 定义类型未知、版本不支持和渲染失败时的降级：展示可读的请求材料，保留通用反馈，明确提示专用交互未加载；不能把未解析的数据当作已完成的结构化回答。

**验收：** 当前 Ramble 完全通过注册入口显示；旧请求保持可读、可编辑、可提交；新增第一方类型不需要复制整个工作台容器。

**本阶段止于：** 一个真实注册项和必要的解析/降级行为。行业插件、远程安装、动态代码加载和通用组件 DSL 留待有实际需求时再考虑。

### 阶段 4：加入 AskQuestion，跑通结构化反馈闭环

**目标：** 默认注册 Ramble 与 AskQuestion 两种工作台，验证抽象确实适用于不同交互。

首版 AskQuestion 支持少量问题、单选/多选、短文本及补充说明。每题与选项有稳定 id；右侧通用 TipTap 始终保留。问题内的输入和右侧自由说明是同一请求的两部分，不能要求用户手动把左侧答案复制进右侧才能提交。

- 参考 `SessionInputForm` 的字段解析、选择和校验，将可复用呈现留在合适的公共模块；不直接把 ACP `SessionInputResponse` 当成 Feedback Request 的结果。
- 先为持久反馈请求跑通 AskQuestion。已有 ACP 即时问答可继续使用原路径；后续如需共用视图，使用显式适配并分别处理返回与恢复。
- 为工作台类型、输入数据、草稿状态和结果设计版本化合同，先改 Rust 源类型，再生成 TypeScript。下面第 6 节列出需要一起解决的持久化与兼容问题。
- 一次提交同时保存题目回答、自由反馈和附件，并产出人类可读的 Markdown 结果以及需要的结构化结果。Agent 取得的是可消费的答案，不只是界面的选中状态。
- 选项不合适时，用户可以仅提供自由说明。明确区分“已回答”“未回答/跳过”“以自由反馈回应”，不能把空答案当成有效选项，也不能让表单校验封死自由反馈路径。

**验收：** Agent 创建 AskQuestion 请求 → 用户选择并补充语音/文字或附件 → 草稿恢复 → 提交 → 原 Agent 取得完整结果。刷新、切换请求、断线、重试、未知类型和只提交自由说明都不丢失内容、不重复发布。

### 阶段 5：Agent 使用说明、首次引导和启用配置

**目标：** 新工作台可发现、可理解、可按用户偏好使用。

- 从注册信息提供简短用途、输入示例和输出说明。Agent 先了解可用类型，再发起请求；具体采用独立查询工具还是能力描述，在协议设计时确定。
- 为每种工作台提供第一次打开时的简短说明，重点讲“这里做什么、如何补充自由反馈、提交后发生什么”。允许跳过与重新打开，避免阻断已有草稿。
- 设置页列出工作台并允许启用/禁用；默认启用 Ramble 和 AskQuestion。保留 Ramble/通用输入作为基础回退，不能关闭到无反馈路径。
- 禁用主要影响新请求的可选范围。已有请求仍可恢复和读取；无法呈现的类型仍保留原始数据与自由反馈入口。
- Agent 可发现的类型需和实际启用策略一致。桌面与 Web Client 的设置作用域、多客户端差异及失效刷新需在实现前明确；布局和引导偏好不要混入业务草稿。

**验收：** Agent 通过说明能正确选择两种类型；每种类型的引导只在应出现时显示；禁用与重新启用不破坏已有请求、草稿或反馈包。

## 6. 引入结构化结果时必须一起设计的合同

以下属于阶段 4 的设计工作，当前不添加这些字段或修改数据库。

| 层面 | 需要明确的规则 |
| --- | --- |
| 请求 | 类型标识、输入 schema 版本和专用数据；省略类型等价于 Ramble；扩展字段参与请求幂等比较。保留现有 `what_happened` 摘要限制，完整问题放在专用数据中。 |
| 草稿 | 自由正文继续以 TipTap JSON 为真源；专用答案/顺序有一个明确、版本化的持久所有者。不要仅存在组件 state、localStorage 或 workspace snapshot。 |
| 一致性 | 明确专用数据是草稿 envelope 的一部分还是关联对象，并建立与正文一致的 revision/CAS 与提交快照。不能发布新答案配旧正文。 |
| 输出 | 提交状态、问题/对象 id、结构化结果、自由正文和附件引用都能被还原。Markdown 是可读投影，不与结构化事实独立编辑。 |
| 整理 | Tidy 保持现有语音整理语义；Cooking 可整理表达，但不能改写选项 id、顺序、跳过状态或用户决定。人类原始输入始终可追溯。 |
| 发布与恢复 | 复用现有反馈包、重试与交付路径，校验、保存和发布的失败不能丢草稿。原请求身份及终态语义不因工作台类型改变。 |
| 升级与降级 | 老请求无需改写即可使用；未知类型/版本的数据保留且可读。旧客户端面对无法安全编辑的专用数据应明确降级，不能悄悄丢字段后保存。 |

不要让专用工作台直接拼接一段 Markdown 就宣称结构化状态已经可靠保存，也不要把每次 UI 点击直接变成 Agent 消息。人类在工作台内可以反复修改，明确提交才形成反馈结果。

## 7. 工作台内部编辑与多模态输入

专用工作区允许输入。例如排序卡片可以改标题、改说明、增删与拖动；AskQuestion 可以有题内的自定义回答。通用输入的存在不意味着所有编辑都必须搬到右侧。

首期内部字段可以使用普通控件，右侧 TipTap 负责完整的语音、截图、附件和整理体验。用户可用通用反馈指出“第二张卡应该改成什么”，这条路径始终可用；后续再逐步支持更直接的字段输入。

要进一步支持“语音写入选中卡片/问题”，推荐引入明确的输入目标：界面显示当前目标，用户主动选择；采集开始时固定请求和目标 id，异步结果回来时仍校验目标和内容版本。焦点变化不能让语音落到另一题，目标已删除时保留待确认原文，允许用户改投通用反馈。

该能力应复用采集与整理服务，通过不同目标的写入适配完成，不给每张卡再安装一个完整 TipTap、录音状态机和附件管线。当前单 Editor 和稳定 owner 约束继续有效；如未来确实需要改变，另写有证据的架构决策。

## 8. 产品定义的同步更新

当前[宪章](CONSTITUTION.md)强调真实体验，并写有“普通确认、权限审批和短问答不是主要价值”。本次讨论提出的扩展，是在现有反馈闭环上支持更多人类参与方式；AskQuestion 上线会超出当前主要旅程的描述。

在阶段 4 落地时，同步记录产品范围修订：保留真实体验和证据反馈作为 Ramble 的优势，同时允许问答、选择和其他人类判断使用专用工作台。更新 `CONSTITUTION.md`、`PRODUCT.md`、`TERMINOLOGY.md` 与必要 ADR，说明协议、数据和里程碑影响。权限审批仍按原有权限合同处理，问答 UI 本身不授予额外执行权限。

本路线中的“Ramble 工作台”“AskQuestion 工作台”指未来可注册的交互类型，不新增宿主会话，也不将现有 Ramble 自由编辑流程重新定义成录音模式。公共容器、类型与 Workbench Client 的正式命名，在注册架构落地时统一写入术语表。

## 9. 后续候选与本轮边界

在两种默认工作台验证完成后，再根据实际使用选择下一种：工作顺序编排、方案对比、局部批注或行业特有的审阅表。排序卡片是当前已讨论的候选，不是本轮承诺的第三个实现。

暂缓：无限画布作为统一容器、任意 Agent 生成 UI、完整 schema-to-UI 引擎、第三方工作台市场、跨行业 SDK、复杂工作流编排，以及 AG-UI/A2UI 协议接入。这些方向需要独立需求和验收，不能作为完成阶段 1 的依赖。

每个阶段结束时，只将已实现的合同和用户行为写入相应当前文档；这里更新阶段状态和提交证据。下一次实施从阶段 1 开始，一次完成并验证一个阶段，再决定是否继续。
