# 文档审阅工作台 v1

状态：第一方 `document_review` v1 合同与设计说明。它复用[反馈协议](../PROTOCOL.md)的请求、草稿、提交和交付，不建立文档编辑器或独立审阅会话。总体决策见 [ADR 008](../adr/008-typed-human-feedback-workbenches.md)。

## 使用场景与界面

Agent 提供完整的 Markdown 文档，例如方案、说明、视频脚本或发言稿。人类阅读标题、列表、表格和代码块等内容，对选中文字、跨段范围或全文添加批注与建议改写。阅读区默认占满工作台，通过“情况说明”查看背景与材料；从“整体意见与提交”打开通用反馈抽屉，补充说明并提交整份请求。顶部持续显示草稿保存状态，抽屉开关不创建第二份正文编辑器。

原文始终只读。批注和替换建议独立保存，不直接修改 Markdown 或项目文件。一个段落可以有多条批注，不因再次选文而把意见写入另一条已有批注。批注只承载意见和建议，不设置待处理或已解决状态；人类最终选择“原稿可用”或“需要修改”，再经统一提交形成结果。选择“原稿可用”不调用最终总结的直接批准入口，也不会自动清除局部修改建议。

选中文字后，工具栏只提供“批注”和“建议修改”。局部编辑卡紧邻所选原文：宽屏放在原文旁，窄屏通常放在对应内容块后；长代码块或原文回退块使块底远离选区时，卡片改在锚点下方浮动并限制高度，内容在卡内滚动。切换布局仍使用同一张编辑卡。完成后收起卡片、继续阅读，原文以低调高亮保留批注位置，可再次打开续写。全文意见仍可从顶栏创建；语音和附件使用各输入字段的共享工具栏。

“建议修改”预填所选原文，理由可选；将替换文本清空即表达删除建议，编辑卡也提供清空操作，选区工具栏不另设删除入口。卡内对照显示原文与建议的变化，原文不会被直接改写。为避免预填超过字段上限，原始引用大于 8000 个 Unicode 标量值时该入口不可用，并提示缩小选区；更长选区仍可批注。删除有内容、附件引用或修改建议的批注需要确认；取消或在确认框按 Escape 后完整保留。空替换文本仍是有效的删除建议，不能按空白批注丢弃。

在局部编辑卡内，点击“完成”或按 Ctrl/Cmd+Enter 仅结束当前批注的编辑并返回原文，不提交整轮反馈；普通批注须先填写意见，修改建议不强制填写理由。刚创建且从未改动的建议仍只是预填原文，不能直接完成；Escape 或收起会移除这条未触碰的新建议。一旦修改措辞或填写理由，收起就保留草稿。Escape 也可保留未完成的普通批注，包括空白批注；提交前仍须补全或明确删除它。输入法组合期间不接管这两个快捷键。局部完成、草稿自动保存与整轮提交是三件事：“完成”不保证后端已保存，保存结果以草稿状态为准；最终选择整稿判断，再从统一提交区提交。

前端在完成和整轮提交前还会提醒处理没有实际意见的建议：若替换文本与对应原文完全相同，理由又为空白，需要修改措辞、补充理由或明确删除该建议。此检查避免把预填内容当作已完成的审阅意见，不改变原始锚点。

Markdown 安全呈现，不执行原始 HTML；安全协议的外链经宿主打开。图片显示替代文字占位，不自动联网加载。无法精确核对映射的内容回退为原始 Markdown 文本，不用猜测的位置创建批注。

## 请求输入

```json
{
  "type": "document_review",
  "version": 1,
  "data": {
    "title": "发布会开场发言",
    "source_version": "draft-3",
    "markdown": "# 开场\n\n大家好😀，今天介绍我们的新产品。\n\n## 要点\n\n- 保留真实体验\n- 提交前检查反馈\n\n| 环节 | 时长 |\n| --- | --- |\n| 演示 | 30 秒 |"
  }
}
```

| 字段 | 含义与限制 |
| --- | --- |
| `title` | 非空原稿标题，最多 200 个 Unicode 标量值。 |
| `source_version` | 非空来源版本标签，最多 128 个 Unicode 标量值；不等于工作台协议版本或草稿 revision。 |
| `markdown` | 非空的完整 Markdown 原文，最多 120000 个 Unicode 标量值。 |

Markdown 原文与 `source_version` 都是不可变请求输入，参与幂等比较。原稿变化时 MUST 创建新请求；不能把旧批注锚点悄悄搬到新内容上。展示时解析 Markdown 不改变持久化的源字符串。

字段长度和数量上限不替代整份消息的预算。请求还受实际 transport 的总 body 上限约束；草稿 `document_json` 继续使用既有 1,000,000 字符总预算。批注引用、意见、建议及自由正文共同消耗草稿预算，不能因为每项单独合法就越过整份保存限制。

## 草稿状态

```json
{
  "type": "document_review",
  "verdict": "changes_requested",
  "annotations": [
    {
      "id": "note-opening",
      "start": 6,
      "end": 10,
      "quote": "大家好😀",
      "kind": "suggestion",
      "body": "先讲听众会得到什么，再介绍产品。",
      "replacement": "一起看看怎样保留真实体验"
    },
    {
      "id": "note-document",
      "start": null,
      "end": null,
      "quote": null,
      "kind": "comment",
      "body": "演示部分请使用实际操作，不作绝对承诺。",
      "replacement": null
    }
  ]
}
```

| 字段 | 合同 |
| --- | --- |
| `verdict` | `null` 表示尚未作出整稿判断；`ready` 表示可以使用，`changes_requested` 表示需要修改。保存允许未完成，提交要求显式非空判断。 |
| `annotations` | 最多 500 条批注；同段可有多条，也可跨段。`id` 是稳定且唯一的批注身份，匹配 `^[a-z0-9][a-z0-9_-]{0,63}$`。数量上限不保证 500 条均可填满每项最大长度。 |
| `start` / `end` / `quote` | 指向完整 Markdown 原文的范围与原始引用；三个字段同时为 `null` 表示全文批注。详见下节。 |
| `kind: "comment"` | 普通批注；`body` 是必填意见，提交时须非空，`replacement` 必须为 `null`。 |
| `kind: "suggestion"` | 建议修改；`body` 是可选理由，可为空，`replacement` 必须为字符串，最多 8000 个 Unicode 标量值。空串表示删除建议，不强制另填理由。 |
| `body` | 必须存在的字符串，最多 4000 个 Unicode 标量值；保存允许空白草稿。提交前普通批注须补全非空意见或移除，修改建议的理由可以为空串或纯空白，但不能省略字段。 |

状态只有整稿判断和批注集合，不再包含 `paragraph_marks` 或 `paragraph_id`。删除某段或某段文字通过选中对应范围并提交 `replacement: ""` 的建议表达。

正文 `doc` 与此状态一起写入版本化 `document_json` envelope，共享 revision/CAS、保存队列、恢复与提交冻结。批注输入复用 TipTap 编辑底座，但持久化仍为独立结构化字符串字段，不合并进正文的 TipTap 文档，也不靠反馈 Markdown 恢复审阅状态。Cooking 不处理原稿、批注、建议文字或整稿判断。

## 文字锚点

局部批注使用**完整原始 Markdown 字符串**中、按 Unicode 标量值计数的非空半开区间 `[start,end)`，并保存该范围的原始 `quote`，满足 `0 ≤ start < end ≤ Markdown 长度`。服务端按不可变原文验证：

```js
[...markdown].slice(start, end).join('') === quote
```

范围可以跨段或 Markdown 块。Markdown 标记、空格和换行都参与计数；不能使用渲染后文本的偏移、DOM 位置、UTF-16 code unit、字节偏移或展示字符宽度代替。例如 `# A😀中B` 的 `[3,5)` 对应 `😀中`。emoji 在本合同中占一个 Unicode 标量值；组合字符可能包含多个标量值，因此索引不能等同于人眼看到的字形数量。

渲染视图的选区必须映射回原始 Markdown，不能直接把可见文本作为 `quote`。不能确定映射时不创建猜测锚点或静默改为全文批注。服务端拒绝越界、三个字段部分为空、引用不匹配等无效锚点。原文只读使同一请求内的锚点稳定，不需要跨版本编辑位置迁移。

## 提交结果与 Agent 消费

成功提交的 `manifest.workbench.result` 为：

```json
{
  "source_version": "draft-3",
  "verdict": "ready",
  "annotations": []
}
```

结果引用原请求来源版本，包含校验后的全部批注；批注字段与草稿一致。`ready` 可以没有批注，但必须由人类显式选择，不允许依靠空白草稿自动推断通过。`changes_requested` 也必须显式选择，具体修改方向可在批注或通用正文中表达。

Agent 应先核对 `source_version` 和原请求 Markdown，再读取整稿判断、全部批注及补充正文。消费局部批注时按原始 Markdown 的 Unicode 标量范围和 `quote` 一起核对，不能对渲染文本套用相同偏移。批注没有解决状态，不能据此推断原稿已修改。`replacement: ""` 是删除建议，不是空值遗漏；RambleDesk 不自动应用建议。

建议是供 Agent 结合上下文修改原文的意见，不是可以机械执行的字符串 patch。选区只覆盖部分 Markdown 格式时，原始 `quote` 可能包含部分格式标记；Agent 处理替换或删除时仍需保留文档结构，并检查周围格式。

请求取消时 `workbench.result` 为 `null`，不发布一个伪造的文档判断。`ready` 和批注都没有执行权限授权含义。Agent 对原稿的修改发生在反馈提交后的正常任务流程中，需要再次审阅时以新稿创建新请求。

## 演进与边界

2026-10-11 按当前使用范围直接替换 `document_review` v1 的分段输入，不提供旧 `paragraphs` 请求、段内锚点或段落标记的迁移。调用方应通过 `describe_workbench` 获取当前 schema，不能继续发送旧字段，也不能把旧段内偏移当成新全文偏移。

Markdown 审阅借鉴 [Plannotator 的任意 Markdown 审阅流程](https://github.com/backnotprop/plannotator/blob/main/apps/portal/ANNOTATE.md)，不只面向计划文档。本合同选择原始 Markdown 标量范围作为批注身份的一部分，不照搬其 DOM 文本定位实现。建议与原文分离也符合 [Google Docs 的建议编辑语义](https://support.google.com/docs/answer/6033474)。

当前不支持直接改原文、多人评论线程、跨版本锚点迁移、视频播放与时间轴、导入 Word/Google Docs 协作历史或自动应用替换。“视频脚本”只是文档使用场景，不表示视频编辑能力。

## 验收重点

批注意见和建议措辞可使用[请求级共享输入](shared-input.md)。切换字段影响下一语音段，已开始的语音保留原目标；人类添加的图片与文件持久化为反馈附件，字段保存对应引用并显示附件标签，与只读请求材料分开。语音或保存重试均不得修改原稿或重复追加已保存文本。

验收覆盖 Markdown 标题、列表、表格、代码块的展示与原文不变；中文、emoji、格式标记与换行的精确范围；同段多条、跨段和全文批注；无效引用拒绝；原文附近编辑、收起后回访与宽窄布局切换不丢内容；局部完成和 Escape 不提交整轮，输入法组合不误完成；已有批注编辑不改变其他锚点或建议；无理由的修改与空串删除建议保存和交付；草稿恢复及正文变换不丢审阅状态；未选整稿判断或普通批注意见为空时拒绝提交；无补充正文也可提交有效判断；取消没有审阅结果。浏览器预览、真实持久化和 Agent 取得结果分别验收，不能相互替代。
